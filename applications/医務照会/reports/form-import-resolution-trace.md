# Form Import Resolution Trace

## Conclusion

The synopsis exports the required form imports. The current resolver helper does not directly consume `ImportedLibraries`, `LotusScriptOccurrences`, or a parent form; it consumes only normalized `owner.source` and `owner.dependencies`. Consequently, passing a handler's source plus an `ImportedLibraries` property leaves the form's libraries invisible. Options Use statements are recognized when explicitly supplied as source, but sibling options records are not discovered or inherited automatically.

The current blueprint also has no retained evidence entries for the three new import surfaces. This establishes an evidence/discovery gap, not whether the blueprint predates the export change or was generated by a discovery path that ignored it.

For the four requested symbols, **146 UNRESOLVED_REFERENCE findings** span **three forms**. All resolve in a controlled replay after supplying form imports and recognizing the known export-footer boundary described below. This is an investigation result, not a modification of the blueprint or proof that the generation pipeline has been fixed.

## Additional Export Boundary Risk

The synopsis Body strings end with export timestamps concatenated directly to closing declarations:

```text
libCommon:      End Function20110915T193242,30+09
clsAddressInfo: End Class20110915T193242,40+09
```

The first replay's strict `End Function\b` / `End Class\b` implementation check rejected these boundaries. That left the 102 `funcReturnMsg` and 14 `clsAddressInfo` finding records unresolved even after imports were supplied; `funcOnErrorMsg` and `funcChkDate` resolved without this adjustment.

For the second replay only, a newline was inserted in memory between the closing declaration and the specifically observed timestamp pattern. All 146 references then resolved to a unique implementation. This is evidence of an export-normalization hazard, not proof that the actual blueprint generator uses that same strict matcher. Do not remove arbitrary numeric suffixes or mark signatures as implementations without checking actual bodies and source boundaries.

## Corrective Contract

1. Normalize all three form import surfaces before resolving child code. Merge imports case-insensitively while preserving original names and evidence pointers; deduplicate repeated exports without losing provenance.
2. Pass the owning form's visibility to its functions, events, and action handlers using explicit owner identity. Do not leak imports across forms or make every library globally visible.
3. Parse Use statements from options with comment-aware lexing. Ignore imports inside comments or string literals; preserve import-source evidence separately from executable call evidence.
4. Recognize verified export-body boundaries before validating implementations, especially class declarations and final routines followed by concatenated footer metadata.
5. Resolve one visible matching implementation automatically. Preserve ambiguity or genuinely absent implementations as review cases; do not suppress unrelated findings.
6. Regenerate the blueprint after wiring the normalization/inheritance path, retaining import evidence and resolution diagnostics. Clear a targeted unresolved finding only after its actual call-site resolution succeeds.
